= POST /api/v1/synopsis - Создать синопсис

[.text-right]
{document-name}.adoc

toc::[]

== Описание
Метод `POST /api/v1/synopsis` запускает новый LangGraph workflow генерации художественного синопсиса.

Пользователь передает свободное описание результата в `message`. Параметры `idea`, `genre`, `style`, `language`, `length` могут быть переданы явно либо извлечены LLM в узле `collect_requirements`.

Для каждого запроса создается новый `thread_id`. Если передан существующий `story_id`, перед анализом требований система пытается загрузить долговременную память произведения через MCP tool `get_story_context`.

Если требований недостаточно, workflow приостанавливается через `interrupt()` и возвращает `status = needs_clarification`. Продолжение такого workflow выполняется методом link:SG-1-U.PostResumeSynopsis.adoc[] с тем же `thread_id`.

Если требования полны, граф выбирает Writer, выполняет цикл Writer -> Critic, языковую редактуру, обновляет StoryMemory и пытается сохранить результат через MCP.

**ПРИМЕЧАНИЕ**: Новый литературный сезон/главу существующей истории следует запускать новым `POST /api/v1/synopsis` с тем же `story_id`. Endpoint `/resume` предназначен только для продолжения прерванного Human-in-the-Loop workflow.

link:https://github.com/C4dB4ne/synopsis_generator[] - исходный код Synopsis Generator

== Доступные роли
Аутентификация и пользовательские роли в текущей версии не реализованы.

[[A1]]
=== A1 Создание thread и начального SynopsisState
API создает `thread_id = uuid4()` и формирует начальный `SynopsisState`.

В state записываются `story_id`, исходный и последний пользовательский запрос + явно переданные требования, лимиты `max_revisions` и `max_clarifications`, а также начальные значения памяти.

`thread_id` передается LangGraph в `configurable.thread_id` и используется PostgreSQL checkpointer для сохранения и восстановления состояния workflow.

[[A2]]
=== A2 Загрузка контекста существующей истории
Если `story_id` не передан, узел `load_story_context` инициализирует пустую память с `story_memory_version = 0`.

Если `story_id` передан, узел получает MCP tools через `MultiServerMCPClient` и вызывает `get_story_context`.

При найденной истории в `SynopsisState` загружаются:

- `story_title`;
- `premise` -> `idea`;
- `genre`;
- `style`;
- `language`;
- `memory`;
- `memory_version`.

Если MCP недоступен или tool вернул техническую ошибку, workflow продолжает работу без загруженной памяти со статусом `story_context_unavailable`.

Если MCP доступен и `story_id` отсутствует в БД, выбрасывается `ValueError`, который API преобразует в `HTTP 404`.

[[A3]]
=== A3 Анализ требований
`collect_requirements` вызывает Ollama через `ChatOllama` и structured output `RequirementsAnalysis`.

Обязательными считаются:

- `idea`;
- `genre`;
- `style`;
- `language`;
- `length`.

Результат LLM объединяется с уже заполненными значениями state. Дополнительно приложение программно пересчитывает `missing_fields`, `ambiguous_fields` и итоговый `requirements_complete`.

Если structured output завершился ошибкой, используется deterministic fallback без LLM: проверяется наличие обязательных полей.

[[A4]]
=== A4 Human-in-the-Loop уточнение
Если `requirements_complete = false` и лимит уточнений не достигнут:

. `request_clarification` формирует уточняющий вопрос через LLM;
. `wait_for_clarification` вызывает `interrupt()`;
. состояние thread сохраняется checkpointer;
. API возвращает `interrupted = true`, `status = needs_clarification` и `thread_id`.

На первой остановке `clarification_count` еще не увеличен. Счетчик увеличивается после получения значения через `Command(resume=...)`.

Если `clarification_count >= max_clarifications`, выполняется `clarification_limit_reached` и workflow завершается без генерации текста.

[[A5]]
=== A5 Создание Story Project
После получения полного ТЗ выполняется `ensure_story_project`.

Для существующего `story_id` новая запись не создается.

Для новой истории через MCP tool `create_story` создается запись `story_projects` с полями `title`, `premise`, `genre`, `style`, `language`. Начальная память создается как `{}` с `memory_version = 0`.

Техническое название `title` формируется из `idea` без отдельного LLM-вызова.

Если MCP недоступен, устанавливается `story_project_unavailable`, но граф продолжает генерацию без постоянного `story_id`.

[[A6]]
=== A6 Выбор Writer по жанру
`genre_router` приводит `genre` к lowercase и последовательно проверяет набор ключевых слов.

[width="100%", cols="5, 5"]
|===
|Genre keywords |Writer
|`фэнтези`, `fantasy` |`fantasy_writer`
|`драма`, `drama`, `драматический`, `dramatic` |`drama_writer`
|`триллер`, `thriller` |`thriller_writer`
|`комедия`, `comedy`, `комедийный` |`comedy_writer`
|Нет совпадения |`universal_writer`
|===

`route_to_writer` дополнительно проверяет, что `selected_writer` входит в разрешенный набор; неизвестное значение заменяется на `universal_writer`.

[[A7]]
=== A7 Генерация draft выбранным Writer
Все пять Writer nodes используют общий `_run_writer` и одну модель `LLM_MODEL` с `temperature = 0.6`.

В prompt передаются:

- текущее ТЗ;
- `latest_user_message`;
- текущий `story_memory`;
- при повторной итерации — текущий `draft` и `revision_instructions`.

Новый явный запрос пользователя имеет приоритет над сохраненной памятью, если пользователь сознательно изменяет ранее установленные факты.

[[A8]]
=== A8 Проверка Critic и цикл доработки
Critic использует structured output `CritiqueResult` и оценивает только текущий `draft`.

Текст считается принятым, если одновременно:

[source]
----
must_revise = false
score >= 8
----

Если текст не принят и `revision_count < max_revisions`, graph route возвращает workflow в ранее выбранный Writer. При реальной ревизии Writer увеличивает `revision_count`.

Если лимит ревизий достигнут, workflow все равно переходит к Language Editor.

[[A9]]
=== A9 Языковая редактура
`language_editor` использует LLM с `temperature = 0.0`.

Редактор исправляет грамматику, орфографию, пунктуацию, повторы и формулировки, но prompt запрещает изменять сюжет, персонажей, события и смысл.

При `critique_passed = true` устанавливается `status = completed`; при переходе из-за лимита ревизий — `status = completed_with_warnings`.

[[A10]]
=== A10 Формирование StoryMemory
`memory_manager` после получения `final_text` формирует новый полный structured snapshot `StoryMemory`.

Структура памяти содержит:

- `summary`;
- `characters[]` (`name`, `role`, `current_state`, `goals[]`);
- `world_facts[]`;
- `locations[]`;
- `unresolved_threads[]`;
- `latest_events[]`;
- `style_rules[]`.

Memory Manager получает предыдущий snapshot, последний пользовательский запрос и `final_text`.

Если LLM не смог сформировать корректный `StoryMemory`, старая память не перезаписывается и устанавливается `story_memory_ready = false`.

[[A11]]
=== A11 Сохранение generation и StoryMemory через MCP
`persist_story` один раз получает доступные MCP tools.

Сначала, если доступен `save_synopsis`, система пытается сохранить generation в `synopsis_generations` и получить `synopsis_id`.

Затем, независимо от успеха `save_synopsis`, если есть `story_id`, `story_memory_ready = true` и доступен `save_story_memory`, сохраняется новая версия памяти.

`source_generation_id` может быть `null`, если generation не удалось сохранить.

При недоступности MCP финальный текст не теряется; `story_memory_saved = false`, а status остается `completed` или `completed_with_warnings`.
